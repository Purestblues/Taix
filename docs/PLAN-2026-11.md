## 三、为什么 N2 必须压到最后一块

想法 2 表面是"界面合并显示"，实质是**统计口径换了主语**：从"应用表 + 网站表"变成"一份屏幕时间实体表"。

推导出的连带影响：

- 概览 / 统计 / 详细 / 分类四页各自直连两套接口，全要换数据源；
- 分类体系要能挂在"网站实体"上（现在网站分类是独立一套）；
- 卡片上显示什么字段（网站显示域名还是站点标题？合并实体显示母项还是展开子项？）取决于实体模型；
- 开关「网站并入浏览器」用**浏览器真实活跃时长**，因此开关切换时总额会变，占比之和可能不足 100%，总表需要能容纳"浏览器内其他页面"这个差额项。

先改视觉再换口径，样式要重排两遍。所以顺序是：定模型 → 做合并 → 换口径 → 再动分类页。

## 四、发版切分

| 批次 | 内容 | 可独立回滚 |
| --- | --- | --- |
| `fork.5` | M5 看板 + G11 | 是 |
| `fork.6` | R1 改名（代码层 → 身份层 + 数据迁移 → 仓库改名，三笔 commit 一次发布） | 是（改名前打 tag 基线，可整批回退） |
| `fork.7` | N4 动效 | 是 |
| `fork.8` | N1 + N3 视觉体系 | 是（纯样式，可整批回退） |
| `fork.9` | N6 子母程序合并 | 是 |
| `fork.10` | N2 统一实体表 + 并入开关 | 是（影响面最大，建议单独一个版本观察） |
| `fork.11` | N5 分类页重做 | 是 |

改名为什么打成一包发：只改代码层不改系统标识，用户完全看不见；而系统标识（安装目录、LaunchAgent、Toast 名）改了不同步迁移数据，历史统计就丢。三者必须同一次装机完成。

## 五、已拍板的口径（实现时不得违反）

1. **「网站并入浏览器」开关打开时，浏览器时长 = 浏览器真实活跃时长**，不是被追踪网站时长之和。开关切换总额会变，差额是"浏览器内其他页面"，必须在总表里有交代。
2. **子母程序合并后，子进程自动继承母进程的分类**，但**子进程原有标签必须保留**（合并是视图期映射层，不销毁原始归属）。将来拆分子进程，它自动回到原分类。
3. **默认视图是统一实体表**（bilibili 30% / chatgpt 30% / Word 40%），开关只改变网站归属（Chrome 60% / Word 40%），不是两套数据源。

## 七、R1 · 改名（已排入 P1）

Taix → **时见 / ShiJian**，全量重命名（含数据目录、安装标识），GitHub 仓库一并改名为 `shijian`，且不再同步上游。

详细方案、影响面、三步顺序与风险清单见 [`docs/RENAME-PLAN.md`](RENAME-PLAN.md)。

排期理由：改名只碰标识不碰逻辑，且现在是改动面最小的时候（571 个文件含 `Taix`）。往后每加一个页面/控件就多一批 `avares://Taix/` 引用，N2 统一实体表还会新增不少文件，越晚做越贵。所以位置定在 `fork.5` 之后、所有功能开发之前。
