## 三、为什么 N2 必须压到最后一块

想法 2 表面是"界面合并显示"，实质是**统计口径换了主语**：从"应用表 + 网站表"变成"一份屏幕时间实体表"。

推导出的连带影响：

- 概览 / 统计 / 详细 / 分类四页各自直连两套接口，全要换数据源；
- 分类体系要能挂在"网站实体"上（现在网站分类是独立一套）；
- 卡片上显示什么字段（网站显示域名还是站点标题？合并实体显示母项还是展开子项？）取决于实体模型；
- 开关「网站并入浏览器」用**浏览器真实活跃时长**，因此开关切换时总额会变，占比之和可能不足 100%，总表需要能容纳"浏览器内其他页面"这个差额项。

先改视觉再换口径，样式要重排两遍。所以顺序是：定模型 → 做合并 → 换口径 → 再动分类页。

## 三·五、N7 · 分类页（"发现页"）信息密度

**问题**：分类页现在是 150×150 的固定方块卡，一张卡只有「图标 + 名称 + 应用数」，
一屏 1440 宽只能放 3–4 个、1080 高只铺两行就到底，下面大片空白。分类一多就要滚动很久，
而每个分类最有用的信息（占用时长、占比、Top 应用）根本没在卡上。

**目标**：同样一屏从 3–4 个提升到 12–20 个，并且每张卡能直接看出「这个分类今天占了多少时间」。

**方案（三步，可独立发布）**

| 步 | 做法 | 数据 | 量级 |
| --- | --- | --- | --- |
| N7-a | 卡片瘦身：150×150 → 宽度自适应、高 96；图标从 40 降到 28，名称 + **时长** + 占比细条；保留应用数做次要信息 | 复用现有分类汇总接口（`api/category/summary` 之类），只取时长 | S |
| N7-b | 视图切换：标题栏加「紧凑 / 卡片」切换（复用 `TabSwitch`），紧凑视图是 4–6 列网格，卡片视图保留现在的方块（但换成新卡片语汇 + 显示时长） | 同上 | M |
| N7-c | 排序与分组：支持按「时长 / 名称 / 应用数」排序；无应用的分类收进折叠区（否则空分类占位） | 本地排序，无需后端 | S |

**不做**：把所有应用平铺进分类页（那是 N5「分类 / 应用」视图的事，等 N6 / N2 的合并实体落地后再做，否则会做两遍）。

**验收线**

1. 1440×900 下首屏至少可见 12 个分类，且无需横向滚动。
2. 每张卡都显示时长；时长为 0 的分类不与有数据混排。
3. 紧凑 / 卡片两种视图切换不丢滚动位置与选中态。
4. 深色与浅色下卡片都是「8px 圆角 + 1px 发丝边 + 零阴影」。

**进度（2026-11-12）**

| 步 | 状态 | 实际做法 |
| --- | --- | --- |
| N7-a | ✅ 已实现，未发版 | 200×92 扁卡片（不用 150 方块）；名字 + 时长同行，应用数在下，底部占比条 + 百分比；目录 / URL 匹配从药丸改成图标右上角小圆点 |
| N7-b | ✅ 已实现，未发版 | 标题栏「紧凑 / 卡片」`TabSwitch`；卡片抽成 `CategoryCard` 控件（应用 / 网站共用），卡片形态靠 `IsCard` 换模板，不换 DataTemplate，滚动位置与选中态不丢；选择走 `[PageState]` |
| N7-c | ✅ 已实现，未发版 | 标题栏「排序」`TabSwitch`（时长 / 名称 / 数量），走 `[PageState]`；三种口径落在 `CategoryCardStats.Sort`：时长（0 时长收尾）、名称（纯字典序）、数量（空分类收尾）；切换只 `Move` 重排，不重拉数据、不重建容器。空分类折叠**未做**（见下） |

**N7-c 的两处口径（2026-11-12）**：

- 排序开关用 `TabSwitch` 而不是下拉菜单：下拉控件 `Select` 只处理 `PointerPressed`、不在 Tab 序列里，
  而分类页在 M3 就已铺过键盘导航；`TabSwitch` 左右键即可切换，样式与「视图」开关同源。
- 「无应用的分类收进折叠区」**没做**：把一列分成「有数据 / 空分类」两套集合后，
  新建、删除、恢复系统分类（会把应用并进去）、重命名这四条路径都要同步两处，
  漏一处就是「新建的分类不显示」；而空分类现在已稳定排在末尾、卡片上不画空进度条、
  时长显示「—」。收益不足以换取这个同步风险，留给 N5「分类 / 应用」视图一起做。

实测 1440 逻辑宽下一行 6 个、纵向约 7 行（≈40 个），远超 12 的目标；只是手头数据只有 6 个分类，所以「≥ 12」是按网格容量算的，不是数出来的。

**排期**：插在视觉体系之后、N6 之前（`fork.8` 发完后作为 `fork.8.5`），因为它是纯展示层改动、不依赖实体模型。

**已拍板的口径（2026-11-12）**：

- 卡片上的时长**只按「今天」算**，本轮**不加周期选择器**（顶部现有 TabSwitch 只是「应用 / 网站」切换）。
- 「408 处硬编码色」这个数字被高估了：实查 `*.axaml` 共 416 处 hex，其中 391 处在 `Theme.axaml`(295) 与
  `Azure.axaml`(96) 里——那是 token 的定义源头（背景光晕渐变 stop、预合成悬停色），不是脏数据。
  散在组件里的只有 25 处 / 13 个文件，已在 `fork.8` 清完。
- `RadiusMedium` 与 `RadiusLarge` 都是 16，语义重复；改动会波及全项目，**与 N7 一起收**，不单独做。
- 列表行进出 stagger 不在 `fork.8`：虚拟化列表复用行容器，容易在滚动时重复触发，单独一批或跟 N7 一起做。

## 五、已拍板的口径（实现时不得违反）

1. **「网站并入浏览器」开关打开时，浏览器时长 = 浏览器真实活跃时长**，不是被追踪网站时长之和。开关切换总额会变，差额是"浏览器内其他页面"，必须在总表里有交代。
2. **子母程序合并后，子进程自动继承母进程的分类**，但**子进程原有标签必须保留**（合并是视图期映射层，不销毁原始归属）。将来拆分子进程，它自动回到原分类。
3. **默认视图是统一实体表**（bilibili 30% / chatgpt 30% / Word 40%），开关只改变网站归属（Chrome 60% / Word 40%），不是两套数据源。

## 六、第二批需求要点（2026-11-13 登记，N8–N15）

> 本节仅登记需求边界与待落地要点，暂未开工。
