# v{version} 更新日志

> 接在 `fork.8.5`（分类页视图与排序）之后。这一版做 **N6 子母程序合并的第一段**：
> 同一个程序的不同版本 / 子进程在列表里合成一行，另加一个可以逐组解散的管理页。
> **只动展示层**：`AppModels` / `DailyLogModels` 一行不改，随时可以拆回原样。

## 主要变化

- **子母程序合并（视图期）**
  - 判定依据只有两样现成的东西：可执行文件所在目录 + 进程名的「品牌」部分。
    `PiDeck-0.9.5-setup`、`PiDeck-0.11.3-setup` 这些版本变体会被折成一行 **PiDeck**
  - 折叠发生在生成列表之前：先按「应用 + 日期」把子成员的时长并进母成员（当天时长最长的那个），
    再算总时长与榜单。所以「总使用时长」「应用量」和榜单三处口径始终一致
  - 合并后的行带一枚「合并 N 项」小徽章，悬停可以看到它把谁并了进来
  - 概览的榜单 / 「更多」卡片（含「比上期」的对比周期）、统计页 Top 榜都已接入
  - 三类东西**永不自动合并**：浏览器（合并了就看不出谁在用）、系统目录（`C:\Windows` 等）、
    以及 `setup` / `uninstall` 这种没有任何辨识度的名字

- **设置页新增「子母程序合并」**
  - 位置：设置 → 常规 → 最下方。列出当前所有自动组，每行显示组名、成员数与成员名单
  - 每一组可以单独「解散」——解散后这一组不再自动合并；右侧「恢复全部」一键清掉所有解散记录
  - 解散记录存在本地的 `app.merge.json`（Windows 在程序目录、macOS 在 `~/Library/Application Support/ShiJian`），
    不进数据库、不上传服务端

## 升级注意事项

1. 本版不带数据结构变更，覆盖安装即可，历史数据不需要迁移。
2. 合并只影响「概览」「统计」两页的列表与计数；分类页的应用列表、搜索结果、Web UI 仍然是逐个应用，
   这是刻意的（合并口径先在客户端落地，服务端实体化在下一版）。
3. 想临时看「没合并」的样子，直接把涉及的分组解散即可，不用卸载。

## 已知问题

- **判定不读发布者信息**：`Publisher` 还没采集，现在同目录 + 同品牌名就算一组。
  好处是能直接覆盖「下载目录里堆着一堆安装包版本」这种最常见的杂乱；
  代价是偶尔会把同目录下名字相近的两个程序并在一起，所以规则做得很保守
  （浏览器 / 系统目录 / 无辨识度名字一律不并）。
- 分类页与搜索结果没有接入合并，所以同一个程序的时长可能在「概览」是一行、在分类页还是两行。
- macOS 产物仍然只验证过「能构建 + 打包成功」，没有 Apple Silicon 机器实机跑过。

## 工程侧

- 自动化测试 99 → **122** 例
  - `AppMergePlannerTests` 23 例：锚点归一化（版本号段 / `bin` 层级 / `.app` 包）、品牌抽取、
    版本变体合并、不同产品不合并、浏览器与系统组件永不合并、母成员选取（时长优先、同分取短路径）、
    解散 / 改名覆盖、按日期折叠（母成员当天没有记录时子行必须保留、总时长守恒）、徽章与悬停文案
- 新增 `Librarys/AppMergePlanner`（纯函数：判定 + 折叠 + 装饰）与
  `Servicers/Instances/AppMergeService`（拉应用表、读写本地覆盖表、60 秒缓存）
- 合并判定与折叠都不依赖界面状态，服务端连不上时静默退化为「不合并」，不影响页面加载
